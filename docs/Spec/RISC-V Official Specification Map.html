Part I — RISC-V Official Specification Map
Universal architecture reference. Does not assume a specific implementation.

1. Architecture Layer Map

The official RISC-V ecosystem is best understood as a layered set of specifications rather than a single ISA document. A CPU/SoC specification should explicitly state which layers it claims to implement, which are unsupported, and which are custom or partial.

Agent rule: do not infer profile, platform, debug, or privileged compliance from an ISA string alone. Treat each layer as an independent conformance target.

2. Official Library Snapshot

The RISC-V Ratified Specifications Library states that it provides access to all ratified RISC-V specifications and that these specifications are maintained by RISC-V International. The RISC-V International ratified specifications page also states that ISA specifications, extensions, and supporting documents are collaboratively developed, ratified, maintained, and publicly available.

4. Agent-Ready Architecture Modules

Each module below can become an independent chapter, implementation ticket, verification plan, or compliance matrix row. The checklist is intentionally phrased as agent tasks.

ISA ArchitectureUnprivileged ISA

1. Base Integer ISA

Define the base software-visible integer instruction set and execution model.

Architecture scope
  • RV32I, RV64I, RV32E, RV64E
  • Integer register file and x0 behavior
  • ALU, branch, jump, load/store, fence, system base instructions
  • Instruction encoding and alignment
  • Illegal instruction and misaligned access behavior
Implementation impact
  • Decoder and immediate generation
  • Register file and ALU datapath
  • Load/store unit and byte enables
  • Trap generation for illegal or misaligned cases
  • Architectural test suite baseline
Agent checklist
  • Declare XLEN and base ISA
  • List every implemented base instruction
  • Define instruction alignment
  • Define misaligned load/store policy
  • Define illegal instruction trap behavior
  • Define reset PC and architectural state

2. Zicsr

Define instructions for accessing control and status registers; CSR contents are defined by privileged and extension specifications.

Architecture scope
  • CSRRW/CSRRS/CSRRC
  • CSRRWI/CSRRSI/CSRRCI
  • CSR read/write side effects
  • Privilege and read-only checks
  • Illegal CSR access behavior
Implementation impact
  • CSR file implementation
  • Decode/execute path for system instructions
  • Precise trap behavior
  • CSR side-effect verification
Agent checklist
  • Implement all six CSR opcodes if claiming Zicsr
  • Handle rd=x0 and rs1=x0 side-effect cases
  • Trap on insufficient privilege
  • Trap on writes to read-only CSRs
  • Document every implemented CSR address and reset value

7. Commercial MCU Recommended Specification Set

This section adds a practical commercial MCU profile on top of the official RISC-V specification map. It is not itself an official RISC-V profile claim. It is a recommended engineering bundle for a production-quality, toolchain-friendly, RTOS-friendly, debuggable, and commercially supportable RISC-V microcontroller.

Important distinction: RISC-V official specifications define architecture-level requirements. A commercial MCU also needs SoC, software, safety, security, test, documentation, manufacturing, and lifecycle deliverables. If a block is not covered by an official RISC-V specification, document it as platform-specific or vendor-specific rather than implying RISC-V conformance.

10.3 Common Platform Contract

All products must provide:

  • Four 64-bit programmable HPM counters HPM3–HPM6 per HPM spec v1.0, with documented machine/URO aliases and mcountinhibit control.
  • A versioned boot/reset contract, memory map, peripheral map, bus-error behavior, linker script, startup code, and BSP/HAL.
