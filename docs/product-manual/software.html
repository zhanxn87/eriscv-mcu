01 / BUILD CONTRACT

Do not substitute a generic -march.

Product-local isa.mk files select the supported ISA/ABI pair. Build the product BSP from its own directory so the linker and image converter use the same memory contract.

M0

make -C eriscv-m0/sw images
make eriscv-m0-bsp

M1

make -C eriscv-m1/sw images
make eriscv-m1-bsp

M2

make -C eriscv-m2/sw images
make eriscv-m2-bsp

Startup

Freestanding startup installs the product trap entry, copies initialized data, clears BSS, and transfers to the application. An RTOS port may retain the copy/clear flow while owning mtvec itself.

Images

The ELF-to-memory converter emits .imem.mem and .dmem.mem. A memory-region violation is an image-generation error, not a runtime warning.

Completion

Examples declare their expected UART, GPIO, tohost, or register oracle in their runner. A command is not considered validated only because it exits.

03 / M2 SOFTWARE RULES

Enable FP state and own DMA buffers explicitly.

M2 applications compile for ilp32f. Floating-point software enables mstatus.FS, treats FCSR as architectural state, and uses the product’s RV32F/Zcf/standard-B declaration. Generic-DMA descriptors and payloads live in System SRAM.

Read the M2 product boundary →
System SRAM
Use .system_sram only for buffers whose CPU/DMA ownership is explicit.
DMA
Direct and descriptor copies are System-SRAM based; UART0 TX is the documented peripheral endpoint.
RTOS FP state
Current FreeRTOS profiles retain an integer ABI until FP register and FCSR task-context save/restore is defined.

04 / RTOS AND BENCHMARK BOUNDARY

Development collateral is not a board-support promise.

FreeRTOS and Zephyr ports are product-local simulation and integration collateral. Their commands and expected completion signals are part of the repository evidence, not a general certification statement.

FreeRTOS M-mode

The M0/M1/M2 M-mode profiles link through the product BSP linker script. M0 FreeRTOS reuses its product startup/UART sources but leaves mtvec to the kernel port; M0/M1 run readonly and initialized data from DTCM after startup copies the ITCM load image; M2 uses the 128 KiB ITCM and DTCM product map.

FreeRTOS U-mode

The M1/M2 U-mode profile deliberately retains a 64 KiB demonstration partition: four 4 KiB user regions plus a 48 KiB kernel region. It is not the full M2 capacity layout.

Zephyr

Each product has a local board/SoC description. M0/M1 Zephyr deliberately retain their standard ROM=ITCM, RAM=DTCM linker model; M2 declares 128 KiB ITCM and DTCM in its board memory regions.

Performance workloads

CoreMark, Embench-IoT, Dhrystone, microbenchmarks, and M2 FP FFT are functional/measurement collateral. M0/M1 readonly-data placement in DTCM is a system software configuration, not a general BSP-driver performance claim.
